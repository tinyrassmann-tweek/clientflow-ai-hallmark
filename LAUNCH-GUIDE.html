Run the complete build locally.

  1. Extract the ZIP and open the ClientFlow-AI folder.
  2. Use Node.js 24 (Node 22.13+ also supports the SQLite development adapter). This project has no third-party runtime dependencies.
  3. Build browser-shared code, then start development mode:
npm run build
npm run dev

Open http://localhost:3000. Development mode uses a fixed local owner account and stores records in .local/clientflow.sqlite. Do not deploy with the --dev flag. Production mode refuses to start without Firebase and owner configuration.

npm test

Nine tests cover lead saving and validation, workspace isolation, viewer permissions, invitation email restriction, approval gates, stale-write protection, cross-origin rejection, disconnected-AI behavior, single-use invitations, and access revocation. Browser QA also verified landing submission → inbox → CRM, specialist drafting, staging → approval → recorded deployment, the three-specialist chain, and 390-pixel landing and app layouts.

Deploy to Google Cloud.

No Google Cloud identity or CLI was connected during this build, so no Google deployment was performed. Use an existing project you control; no paid Google resources were provisioned here.

  1. Open Google Cloud Console and select the intended existing project. Confirm billing and a budget appropriate for your zero-spend-until-profitable rule before provisioning billable services.
  2. In the Firebase Console, add Firebase to that same project if necessary. Enable Email/Password sign-in under Authentication. Record its web API key. Create the owner account using the email you will set as CF_OWNER_EMAIL, then verify that email.
  3. Use a Standard edition, Native mode, (default) Firestore database in the selected project. The adapter targets this API. If the project already contains other data, inspect the existing database and rules before deploying. A dedicated project gives this app its own boundary.
  4. Keep direct client access to the clientflow collection denied. This app accesses records through the Cloud Run service account, not a browser Firestore SDK. The runtime service account receives roles/datastore.user. The application checks workspace membership itself. Existing broad “allow” rules must not expose this collection.
  5. Upload/extract the complete build in Cloud Shell and open its folder. Set the following non-secret configuration values, then run the included script. The web API key identifies the Firebase project; it is not an admin key. Never paste service account private keys or AI secrets into chat.
export CF_PROJECT='your-existing-project-id'
export CF_OWNER_EMAIL='your-owner-email'
export CF_FIREBASE_API_KEY='your-firebase-web-api-key'
export CF_REGION='us-east1'
bash scripts/deploy-google.sh

The script checks for the database, enables required APIs, creates a dedicated runtime service account if missing, grants database access, and deploys the application to Cloud Run. It uses a public HTTP service so visitors can reach the marketing page and lead form; workspace endpoints still require a verified Firebase identity and membership. It may require IAM permissions for the deployer and Cloud Build service identity; follow the service error if your project uses restricted deployment policies.

After deployment, add the Cloud Run host and eventual custom domain to Firebase Authentication’s authorized domains. Configure the verification email action handler through Firebase Hosting/its managed action links; leave the default Firebase email action handler intact unless you deliberately replace it. Test confirmation from a new account and confirm that unverified accounts cannot open saved workspaces.

AI generation.

Set OPENAI_API_KEY as a server-side secret, and optionally set OPENAI_MODEL to a model available in your project. The default configured name is gpt-4.1-mini; model access must be verified in your account. This build uses the Responses API, requests store:false, and limits each workspace to 20 requested AI drafts per hour. It sends only the entered brief, not the full CRM. Treat submitted source text as client data and obtain permission before sending it to any provider.

For Cloud Run, use Secret Manager and a secret binding to OPENAI_API_KEY. For the hosted Site review, configure the same name in its environment settings. Template mode needs no AI provider. A configured key makes the AI option available; a real generation still needs a successful provider request.

Your custom domain.

Deploy first and verify the returned Cloud Run URL. Then use Cloud Run domain mappings or an HTTPS load balancer and follow Google’s exact DNS instructions. Update Firebase authorized domains. Test HTTPS, landing form persistence, owner login, invitations, and tenant isolation at the final domain before announcing the launch.
